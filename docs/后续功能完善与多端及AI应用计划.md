# Campus Pulse 后续功能与运营后台 / AI 应用计划

> 状态：**Owner 已确认；Stage C1 本地运营后台已实现并完成首轮测试；其它 AI 扩展待后续确认**
> 日期：2026-09-30
> 项目：Campus Pulse / 校园燃动

## 1. 本次术语与范围澄清

Owner 所说的“多端”是指**用户微信小程序 + 运营后台**两个操作端，不是让学生账号先支持跨手机同步。

本阶段实施目标：

1. 新增独立 Web 运营后台；
2. 让 Web Admin 与微信开发者工具模拟器通过同一个本机 API 维护/读取挑战和公告配置；
3. 配置在开发机本地持久化，学生运动记录和完整轨迹仍只留在小程序本地；
4. 后台服务仅绑定 `127.0.0.1`，用于研究演示，不开放公网；
5. 不接生产数据库、微信真实登录或云端学生账号。

## 2. 当前基线

已实现并推送的能力包括：

- 小程序首页、周/月趋势、运动记录列表/详情、前台定位、榜单、挑战详情、勋章、隐私设置、目标和本地反馈草稿；
- 周/月统计、连续运动、挑战和勋章等由本地运动记录派生；
- 小程序可选连接本机 AI 代理；运动复盘在代理运行时已通过开发者工具模拟器验证；
- AI Key 仅从代理进程环境读取，不在小程序或仓库中。

当前仍为本地研究原型：

- 学生身份、运动记录和真实 GPS 轨迹不上传；
- 榜单其他同学与参与人数仍为演示数据；
- 没有云端 API、数据库、后台账号、多人同步、真实运营或服务端权限。

## 3. 本地运营后台设计

### 3.1 目标架构

```text
微信小程序模拟器 ─┐
                  ├─ 本机 Admin API ─ 本机 JSON 配置库
Web Admin 浏览器 ─┘

小程序运动记录和 GPS 轨迹 ─ 继续保存在 wx storage，不进入 Admin 配置库
AI 复盘 ─ 小程序 → 本机 AI 代理 → API 网关
```

计划的开发地址：

```text
Web Admin： http://127.0.0.1:8790/
Admin API： http://127.0.0.1:8790/api/admin/*
小程序公开配置： http://127.0.0.1:8790/api/public/*
AI 代理：   http://127.0.0.1:8788/
```

### 3.2 本阶段功能

Web Admin 首版包含：

- **运营概览**：挑战数、已发布挑战数、公告数、最近配置操作；
- **挑战管理**：创建、编辑、发布/下架、删除；配置标题、说明、规则类型、目标、周期和演示奖励；
- **公告管理**：创建、编辑、发布/下架、删除；
- **操作记录**：只记录本地配置变更类型和时间，不记录用户运动数据或密钥；
- **本机持久化**：JSON 文件保存 Admin 配置；开发机服务重启后配置仍在；
- **小程序读取**：进入活动页时读取已发布挑战；首页可读取已发布公告；API 停止或请求失败时回退到本地默认演示数据。

### 3.3 数据边界

本机配置库只保存：

- 挑战/活动定义；
- 公告定义；
- 本地操作审计摘要。

不保存：

- 小程序用户身份、昵称、手机号；
- 运动记录、精确轨迹、位置历史；
- API Key、Secret 或授权凭据。

本机数据路径放在 Git 忽略目录。JSON 写入需用临时文件加原子重命名，避免中断破坏存储。

### 3.4 本机安全边界

- Node Admin API 仅监听 `127.0.0.1`，不接受 LAN/公网访问；
- 当前不设登录/RBAC，因为这是 loopback-only 本机原型，不代表真实管理员权限；
- 不提供对任意文件路径的读写，不输出模型 Key，不保存模型请求内容；
- 若以后需要其他电脑的运营人员访问，必须另立生产后端安全计划：登录、RBAC、CSRF/来源校验、审计、备份、HTTPS、Secret 托管和部署隔离。

## 4. 学生多设备同步：当前不实施

本阶段的小程序 + Admin 双端共享的是**挑战与公告配置**，不是学生个人运动数据。

| 目标 | 当前是否做 | 说明 |
| --- | --- | --- |
| 用户小程序 + Web Admin 运营配置 | 是 | 通过本机 API 和本机 JSON 文件共享挑战/公告 |
| 学生换手机恢复运动记录 | 否 | 需要真实登录、云端数据库和数据删除机制 |
| 多名学生共享实时榜单/参与挑战 | 否 | 需要服务端身份、校验、防刷榜和数据治理 |
| 单人演示和交互可用性测试 | 支持 | 继续用本地 storage，不需要云服务 |
| 研究社交激励对真实行为的影响 | 当前不支持 | 招募参与者并开展真实社交试验前需设计多用户后端与伦理/隐私流程 |

**决定：** 先实现本机 Web Admin 双端原型，不顺手扩成学生多设备或生产系统。

## 5. AI 应用可行性和后续顺序

### 5.1 AI 运动复盘（已接入）

在运动详情页主动点击后，只发送距离、时长、配速、本周运动次数/总里程和目标；不发送轨迹、昵称、微信身份或日期。代理校验 JSON，失败时回退本地模板。使用新 Key 前，应先撤销曾粘贴到对话中的旧 Key。

### 5.2 AI 挑战推荐（高可行，后续阶段）

规则先筛选合法挑战，模型只负责在候选项中排序/解释；结果需 schema 校验和规则复核。模型不能新造目标、奖励、排名或完成状态。

### 5.3 AI 打卡文案（高可行，后续阶段）

按聚合运动统计生成可编辑草稿；用户预览后复制/主动分享。尊重“允许好友看到打卡”设置；不自动发帖、不包含完整轨迹。

### 5.4 校园运动问答（中高可行，依赖权威资料）

需要学校确认的场馆时间、活动和安全资料。首版可用本地 FAQ + 关键词/BM25 检索，不需要先上向量数据库。没有可信资料时不得让模型编造校园政策。

### 5.5 AI 内容审核（文本可做演示，真实运营需人工工作流）

当前没有真实 UGC。可在后续用合成评论演示“允许/复核/拒绝”建议和审核队列；模型不得自动封号、删除真实内容或处罚。图片审核和真实用户审核暂不做。

## 6. 阶段和验收

### Stage C1：本地 Admin + 配置 API（Owner 已确认，首轮完成）

- Web Admin 挑战/公告 CRUD；
- 本机 JSON 持久化和审计摘要；
- 小程序读取发布配置并有离线回退；
- API 只监听 loopback；
- 不动个人运动记录和轨迹。

### Stage C1 验收标准

- 新建/修改/发布/下架/删除挑战，重启后状态仍在；
- 新建/修改/发布/下架公告，首页只展示已发布公告；
- 小程序活动页显示后台发布挑战，代理/API 关停后回退本地数据；
- 表单校验、JSON 持久化原子性、公开配置过滤与失败回退有自动化测试；
- 没有 API Key、用户身份或 GPS 坐标进入 Admin 数据文件；
- Web Admin 能在微信模拟器外用浏览器访问 `127.0.0.1:8790`。

### 后续 Stage C2：学生多用户/真实运营（需另行评审）

仅在研究方案明确需要真实多人社交、跨设备恢复或外部运营后，另行提交影响面计划，再设计服务端登录、数据库、RBAC、迁移和生产部署。

### 后续 Stage D：AI 推荐/文案/FAQ/审核

AI 运动复盘完成独立验收后，再按 5.2–5.5 逐项实现和测试，不默认一次性全部启用。
