## 1. 计划目的

本文件用于盘点当前研究展示版的功能遗漏，并提出一套可控的大模型应用开发融合方案。

在 Owner 确认前：

- 只进行方案讨论、只读检查和测试设计；
- 不新增业务代码；
- 不接入真实大模型 API；
- 不配置任何模型 API Key、云函数、数据库或生产域名；
- 不采集、上传或处理真实用户运动轨迹。

## 2. 当前基线

### 2.1 已完成能力

当前原型已经具备：

- 首页运动统计、周目标进度和趋势图；
- 演示模式运动记录；
- 前台定位模式基础流程；
- 运动距离、时长、配速、热量和轨迹展示；
- 周榜/月榜；
- 线上挑战加入和退出；
- 勋章墙；
- 本地隐私设置；
- 本地运动记录删除；
- 中文 README、研究设计、影响面计划和安全边界 Skill；
- WXML 禁止直接调用 JavaScript 方法的修复；
- 地图折线至少两个有效点和异常坐标校验。

### 2.2 当前技术边界

```text
微信小程序原生页面
    ↓
页面 JavaScript
    ↓
本地 storage
```

当前没有：

- 真实微信登录；
- 服务端 API；
- 数据库；
- 服务端榜单计算；
- 服务端挑战和勋章计算；
- 多用户社交动态；
- 大模型 API；
- 云函数或模型代理层。

因此，大模型融合不能直接把 API Key 放进小程序，也不能让模型直接决定排名、勋章、奖励、运动安全或用户权限。

## 4. 大模型融合目标

大模型只作为“解释、推荐、生成和辅助决策”能力，不作为最终事实来源和高风险决策者。

建议采用以下闭环：

```text
规则和统计计算可信数据
    ↓
大模型解释、总结、推荐或生成文案
    ↓
结构化结果校验
    ↓
安全过滤和降级
    ↓
用户确认后展示
```

## 5. 推荐的大模型功能

### 5.1 AI 运动复盘教练（首选功能）

运动结束后根据聚合数据生成简短复盘：

输入示例：

```json
{
  "distance_km": 3.8,
  "duration_minutes": 29,
  "pace": "7'38\"",
  "recent_sessions": 4,
  "weekly_goal_km": 10,
  "weekly_completed_km": 7.4
}
```

输出只允许包含结构化字段：

```json
{
  "summary": "本次完成 3.8 公里，用时 29 分钟。",
  "positive_feedback": "比上一周平均里程有所提升。",
  "next_action": "建议本周再完成一次 2 至 3 公里的轻松跑。",
  "safety_note": "如出现不适，请停止运动并寻求专业帮助。"
}
```

边界：

- 不上传原始轨迹；
- 不上传昵称、微信身份或精确位置；
- 不生成医疗诊断；
- 不给出高风险训练建议；
- 模型失败时显示规则模板；
- AI 文案不影响里程、排名、挑战进度和勋章。

### 5.2 AI 个性化挑战推荐

根据用户选择的目标和近期统计数据推荐挑战：

- 目标：规律运动、提升里程、轻量社交、尝试校园路线；
- 可用时间：工作日、周末或自定义；
- 当前基础：近 7 天运动次数和累计里程；
- 社交偏好：个人挑战、好友挑战、社团挑战。

推荐结果必须经过规则约束：

- 目标里程不能超过安全配置上限；
- 不推荐连续高强度运动；
- 不把排行榜名次作为唯一目标；
- 必须解释推荐原因；
- 用户可以拒绝或重新推荐。

### 5.3 AI 打卡文案助手

用户完成运动后，可以选择生成：

- 简洁记录风格；
- 轻松鼓励风格；
- 社团号召风格；
- 研究展示风格。

第一阶段可以使用本地模板模拟；接入真实模型时必须：

- 只传聚合运动数据；
- 不默认公开完整轨迹；
- 用户编辑和确认后才能分享；
- 生成内容必须经过敏感内容检查。

### 5.4 校园运动问答助手（后续）

在有正式校园资料后，使用检索增强生成提供：

- 校园运动场地开放时间；
- 校园活动规则；
- 挑战赛说明；
- 运动安全提示；
- 小程序功能帮助。

该功能需要正式的资料来源、更新时间、权限和引用展示，不能让模型凭空回答学校政策。

### 5.5 AI 内容安全辅助

如果后续加入真实打卡动态和用户评论，可以用模型辅助识别：

- 人身攻击和骚扰；
- 仇恨或歧视内容；
- 危险运动鼓动；
- 隐私泄露；
- 广告和刷屏内容。

模型只能提供审核建议，最终处置应保留规则、人工复核和申诉机制。对于公开 UGC，内容审核必须在服务端或受控代理层完成。内容安全 API 可用于文本或图像输入分类，但阈值和处置策略仍需项目自行定义。

## 6. 推荐的大模型技术架构

### 6.1 当前研究展示版：本地 AI Mock

第一步不接真实模型，先实现统一的本地接口：

```text
页面
  ↓
aiService.generateWorkoutReview(input)
  ↓
本地 mock 响应
  ↓
结构化卡片展示
```

目的：

- 先验证交互；
- 不泄露 Key；
- 不产生网络费用；
- 不依赖后端；
- 方便答辩演示和离线运行。

### 6.2 后续真实模型：服务端 AI Gateway

如果 Owner 后续确认接入真实模型，建议采用：

```text
微信小程序
    ↓ HTTPS
AI Gateway / 云函数
    ├── 身份校验
    ├── 输入脱敏
    ├── Prompt 模板
    ├── 模型适配器
    ├── 结构化输出校验
    ├── 内容安全检查
    ├── 超时/重试/限流
    ├── 日志脱敏
    └── 失败降级
        ↓
模型供应商 API
```

严禁：

- 在小程序代码中写入 API Key；
- 让客户端直接调用模型供应商；
- 将精确轨迹和微信身份发送给模型；
- 让模型直接写数据库；
- 让模型直接修改榜单、勋章或奖励。

### 6.3 技术能力建议

大模型应用开发可以体现以下技术点：

1. **结构化输出**：让模型返回固定 JSON，而不是直接返回任意长文本；
2. **工具调用/函数调用**：模型只能调用受限的只读统计工具，例如查询本周里程；
3. **RAG**：后续对校园运动规则、场地资料和活动文档做检索增强；
4. **内容安全**：对打卡文案和评论做模型辅助审核；
5. **可观测性**：记录 prompt 版本、模型版本、耗时、错误和降级次数，不记录原始隐私数据；
6. **评测集**：准备运动复盘、推荐安全、隐私拒绝和异常输入样本，比较输出是否符合规则；
7. **成本控制**：限制文本长度、调用频率和最大输出，优先使用本地模板降级。

如果最终选择 OpenAI 作为模型供应商，可在服务端适配 Responses API 的结构化输出、工具和文件检索能力；OpenAI 官方文档也提供了 vector stores、file search 和 evals 等能力，但本计划不在确认前锁定供应商或模型型号。

## 9. AI 数据边界

### 允许发送给模型的候选数据

- 距离区间或聚合距离；
- 运动时长；
- 平均配速区间；
- 近 7 天运动次数；
- 目标完成比例；
- 用户主动选择的运动目标。

### 默认禁止发送

- 微信 OpenID、UnionID、手机号；
- 昵称、头像和学院等直接身份信息；
- 原始经纬度和完整轨迹；
- 精确运动时间线；
- 私密社交关系；
- 未经用户确认的打卡内容；
- 任何 Secret、Token 和本地配置。

### 模型输出限制

模型输出必须经过：

```text
Schema 校验
    ↓
敏感内容检查
    ↓
安全规则校验
    ↓
长度和格式限制
    ↓
失败则使用本地模板
```

## 10. 研究价值

加入大模型后，研究问题可以扩展为：

1. 个性化 AI 反馈是否比固定模板更能增强运动目标感；
2. AI 推荐的挑战是否比随机挑战更容易被接受；
3. AI 生成的打卡文案是否提高分享意愿；
4. 用户是否信任 AI 运动建议并理解其局限；
5. 结构化数据、规则引擎和大模型生成之间如何分工；
6. AI 功能带来的激励收益是否值得其隐私、成本和误导风险。

研究中应区分：

- 功能可用性；
- 用户主观接受度；
- 行为指标变化；
- 模型质量；
- 安全与隐私风险。

不能仅凭模型生成文案好看，就宣称提高了运动坚持性。

## 13. 当前执行状态

Owner 已确认：阶段 A 先完成功能补齐，阶段 B 使用提供的兼容 API 做 AI 运动复盘测试。阶段 A 已完成并推送，功能和验证结果见 `docs/第二阶段功能补齐实施记录.md`。
