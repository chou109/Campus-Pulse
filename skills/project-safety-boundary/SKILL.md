# Project Safety Boundary

## 1. 适用目标

本 Skill 用于把“能不能改、改什么、改到哪里、如何验证”说清楚，尤其保护本项目中的：

- 微信小程序代码、页面和本地演示数据；
- 用户身份、运动记录、位置轨迹、健康统计和社交可见性；
- 后端接口、数据库、排行榜、挑战、勋章和奖励规则；
- 微信 AppID、合法域名、Secret、证书和发布配置；
- 未提交代码、本地环境、测试数据和共享服务。

迁移的是工程流程和安全边界，不迁移参考项目的名称、端口、框架、数据库、角色、环境变量或部署命令。

## 2. 不可越过的红线

未经 Owner 明确授权，不得：

- 连接、写入、迁移或清理生产/共享数据库；
- 修改真实 `.env`、微信 Secret、证书、云资源或生产配置；
- 执行 `git reset --hard`、破坏性 `git clean`、批量删除或覆盖用户已有改动；
- 推送、合并、发布、重启共享服务或切换真实流量；
- 发送真实通知、消息、积分、勋章、奖励或支付；
- 默认启用后台定位、通讯录、相册、麦克风、摄像头等非必要权限；
- 把客户端传来的 `userId`、里程、排名、勋章或管理员标记当作可信事实；
- 把“监听端口、配置 URL、构建成功、页面能打开”当作完整联通或发布证据。

## 3. 开始任务：先建立事实基线

先检查项目规则和工作区：

```bash
pwd
git status --short --branch
git branch --show-current
git log -1 --oneline
find .. -name AGENTS.md -o -name CLAUDE.md -o -name CONTRIBUTING.md
find . -maxdepth 3 \( -name package.json -o -name project.config.json -o -name pyproject.toml -o -name go.mod \)
```

读取 `README.md`、开发规则、测试说明、部署说明和现有设计文档。确认：

- 当前项目真实入口、目录、运行时和启动方式；
- 前端、后端、Domain、Repository、Worker 的边界；
- 身份来源、权限校验位置、数据库和 migration 位置；
- 哪些页面是演示模式，哪些操作会产生真实副作用；
- 微信定位、分享、订阅消息和其他平台权限的现状。

将结论标注为：

- **已验证事实**：有文件、命令输出或测试证据；
- **仓库推断**：合理但尚未运行验证；
- **Owner 待确认**：需要产品、数据或运维负责人决定；
- **未知**：不能猜测。

## 4. 工作区保护

- 保持最小修改面，不覆盖用户已有改动；
- 不修改与当前任务无关的文件；
- 不把本地演示数据、日志、轨迹或用户导出文件提交到 Git；
- 不提交 `.env*`、密钥、证书、真实 AppID/Secret 和包含 PII 的文件；
- 发现已有修改时，先用 `git status`、`git diff --stat` 和定向 `git diff` 区分归属；
- 临时文件放入 `work/` 或系统临时目录；
- 除非明确要求，不主动 commit、push、merge 或 publish。

## 5. 风险分级

### L0：只读分析

读取仓库、配置、日志和文档；可以输出方案、测试矩阵和风险清单；不得修改业务代码。

### L1：低风险本地修改

文案、样式、页面空态、纯函数和测试；不改变数据模型、权限、外部副作用或发布配置。

### L2：受控功能修改

定位、运动数据、排行榜、挑战、勋章、社交可见性、登录、API、数据库 schema 或跨层契约。
必须先写影响面计划并得到 Owner 确认，完成定向测试后再交付。

### L3：高风险操作

真实用户数据、生产数据库、Secret、真实消息/奖励、迁移、回滚、发布、流量切换或共享环境。
必须单独确认目标环境、时间窗口、回滚方式、操作者和验收证据。

## 6. 计划确认门禁

以下变更在编码前必须先给出影响面计划并等待 Owner 明确确认：

- 数据库字段、索引、约束、migration、回填或删除；
- 登录、Session、身份绑定、管理员权限或 RBAC；
- 位置、健康数据、运动轨迹、社交关系、UGC、榜单和奖励规则；
- 微信定位、分享、订阅消息、支付或其他外部接口；
- 跨页面/跨服务/跨 Worker 的功能；
- 生产配置、合法域名、Secret、部署和回滚。

计划至少包含：目标、非目标、现状、影响文件、数据流、权限边界、隐私风险、回滚方案、测试矩阵、验收证据和未解决问题。

计划确认不等于 migration、生产连接或发布授权。

## 7. 位置与运动健康数据

- 默认只做前台定位；后台定位需要单独的产品和平台授权；
- 在采集前说明用途、时机、字段、保存周期和删除方式；
- 允许用户停止记录、删除记录和撤回分享；
- 轨迹展示优先使用抽样、模糊化或只展示统计结果；
- 日志、埋点、截图和测试数据必须脱敏；
- 公开榜单只展示必要昵称、头像和统计数据；
- 不把运动数据当作医疗诊断、身体能力证明或安全保证；
- 高强度挑战和奖励机制要有安全提示、退出机制和异常检测。

## 8. 分层与权限原则

- **Domain**：schema、枚举、规则、错误码；不执行 IO；
- **Application**：用例编排、事务、不变量和服务端权限后的判断；
- **Repository/Infrastructure**：数据库、存储、外部 API、缓存和队列；
- **API/Route**：读取登录态、校验输入、调用用例、统一错误响应；
- **UI**：负责展示和交互，不最终决定权限、排名、奖励或数据归属；
- **Worker**：异步任务要幂等、可重试、可观测，默认关闭真实副作用。

服务端或受控规则必须计算：运动记录归属、排行榜、挑战完成度、勋章解锁和奖励发放。客户端传入的数据只能作为候选输入，不能直接决定权限或结果。

## 9. 数据库和 migration

1. 先只读检查当前 schema、migration 状态、备份和回滚能力；
2. 说明兼容窗口、锁表风险、回填规模和旧客户端影响；
3. migration 与业务代码分开审查；
4. 未经单独授权不执行共享或生产 migration；
5. 迁移后验证 schema、关键查询、写入路径和旧数据；
6. 失败时停止扩散，不用删除数据或重建数据库掩盖问题。

## 10. 测试与完成证据

按改动范围执行：

- 纯逻辑：单元测试、边界值和异常输入；
- API：schema、身份、越权、重复提交、幂等和错误响应；
- 定位：授权拒绝、定位失败、低精度、跳点、重复点和停止记录；
- UI：加载、空态、失败态、窄屏、页面切换和重复点击；
- 社交：隐私设置、取消分享、举报/屏蔽和刷榜风险；
- 发布：健康检查、登录、关键读写、错误日志和副作用开关。

结束时必须说明：运行过的命令、通过/失败结果、未验证部分、Owner 待确认项和工作区状态。不得只说“已完成”。

## 11. 分支与发布

### 阶段完成后的自动交付（Owner 已授权）

本项目 Owner 已明确要求：每个用户确认的功能阶段完成并通过测试后，自动执行中文 Git 提交并推送当前远程分支。遵循以下门禁：

1. 先运行该阶段适用的测试、`git diff --check` 和秘密扫描；
2. 确认没有 Secret、真实用户数据、`project.private.config.json` 或无关改动；
3. 使用中文提交备注；
4. 推送前确认当前分支和远程目标；
5. 推送后验证远程分支 SHA 与本地提交一致；
6. 如遇远程分叉、冲突、权限失败或测试失败，停止自动交付，不强制覆盖、不伪称成功，并报告阻塞。

该授权只覆盖完成且已确认的阶段，不包括生产发布、数据库迁移或任何未经单独批准的真实外部副作用。

### 提交信息规则

- Git 提交备注默认必须使用中文；
- 提交信息应说明本次改动的目的，例如：
  - `初始化 Campus Pulse 校园燃动小程序`；
  - `修复运动轨迹折线渲染错误`；
  - `完善研究展示版部署说明`；
- 提交前检查 staged diff，确认没有 `project.private.config.json`、环境变量、Secret、证书、真实用户数据或位置轨迹；
- 除非 Owner 明确授权，不主动 commit、push、merge 或 publish；本次获得明确授权后才执行。

推荐流程：

```text
读取规则 → 检查工作区 → 影响面计划 → Owner 确认
→ 功能分支 → 分层实现 → 定向测试 → 完整检查
→ Review → 授权后提交/推送 → 发布验收
```

发布前确认正确分支和 commit、配置 profile、Secret 注入、数据库兼容性、外部副作用开关、Worker 状态和回滚点。发布后验证登录、关键读写、权限、错误日志、队列和真实副作用；关键检查失败时停止继续发布。

## 12. 项目适配记录

在本文件或项目文档中记录已验证的项目专属事实：

- 微信开发者工具配置、AppID 和合法域名；
- 真实启动、构建、测试和发布命令；
- 端口、数据库、队列和 Worker 归属；
- 位置权限和隐私协议状态；
- 常见构建、授权和发布错误；
- 尚未验证的外部环境和运营能力。

不得把项目专属事实写成通用假设。

## 13. 完成标准

只有在以下事项都已说明，才可声明任务完成：

- 需求目标、非目标和安全边界清楚；
- 现有工作区未被破坏；
- 权限和数据归属由服务端或受控规则保障；
- 位置、健康和社交数据遵循最小采集、脱敏和可撤回原则；
- 必要测试、类型检查和格式检查完成；
- 数据库、Secret、外部副作用和发布授权状态明确；
- 工作区、提交、推送和发布状态明确；
- 未验证项和后续风险已列出。
